Status: **approved**. The DDL is in [`/migrations`](../../migrations) (goose, 11 files, 34 tables). `scripts/db-test.sh` checks it with 80 schema tests (`db/tests/schema_test.sql`) plus an up/down/up cycle, and passes on PostgreSQL 16 and 18.
**Implementation:**
- **M0** (foundation) is complete: the platform kernel, the Go and Vue shells, CI and the lint guards. The runtime lock-order enforcement is `db.LockRows` / `db.EnterLockLevel`.
- **M1** (tenancy and business day) is complete: property setup, `BusinessDayService` (the only source of the business date, including the night-audit time guard and `CloseAndOpenNext` for M13), gapless document numbers, the audit writer, and sqlc.
  - Charge-code seeding on property creation moved to M5 (done there).
- **M2** (identity and access) is complete. JWT access tokens (15 minutes, in memory) and rotating refresh tokens in an httpOnly `SameSite=Strict` cookie.
  - Refresh-token reuse ends all of a user's sessions. Migration 00012 adds `user_sessions.revoked_reason`, so detection only fires for rotated tokens, not for a stale tab after logout. There is a 30-second grace window for tabs that refresh at the same moment.
  - Sessions are re-checked on every request, so revocation is immediate.
  - Passwords use argon2id (OWASP parameters). Login gives one generic error, has timing equalisation and is rate-limited (in-memory per instance, Redis later).
  - Authorization is per property: 404 without access, 403 without the permission. Users, roles and property creation are for tenant administrators.
  - The M1 development header login was removed.

- **M3** (rooms, blocks, housekeeping) is complete. No migration: the tables already exist in 00004.
  - `internal/rooms` owns room types, rooms and OOO/OOS blocks. `internal/housekeeping` owns the current status, its append-only log and the board; `housekeeping.Service.MarkDirty` is the entry point M10/M12/M13 use for system-driven changes (source CHECK_OUT, ROOM_MOVE, NIGHT_AUDIT, CHECK_IN_REVERSAL).
  - Conflict checks already read the M8/M10 tables: a block, a room type change or a room deactivation is rejected (409 `ROOM_BLOCK_CONFLICT` / `ROOM_IN_USE`, with `context.conflicts`) while an open stay segment or a CONFIRMED assigned line holds the room. An overstay holds the room through tonight (`GREATEST(departure, BD + 1)`).
  - The type-level `available ≥ 0` check (`INVENTORY_OVERSOLD`) on blocks, block extensions, type changes and deactivation landed with the availability engine in M8. Room type deactivation only checks active rooms and future CONFIRMED lines of the type, as specified.
  - Room type codes are immutable (PATCH rejects `code`). `GET {P}/room-status` (the full derived board) stays in M10; the housekeeping board already carries derived occupancy and the active block.
  - The housekeeping board is not paginated (one row per active room, capped at 2,000).

- **M4** (guests) is complete. Migration 00013 adds `tenant_sequences` (gapless tenant-wide guest numbers) and the SQL function `guest_linked_to`, the single definition of "a guest is linked to a property".
  - `auth.Authorizer.PropertiesWith(perm)` lists the caller's properties holding a permission. Tenant-wide resources use it to derive visibility; the visibility, write and history rules are in [06-api.md §8](06-api.md).
  - Duplicate hints never block creation; look-alikes at properties the caller cannot see are counted, not shown.
  - Search is prefix and token based on the existing btree indexes. `pg_trgm` (fuzzy matching) is still later. Phone numbers are compared by digits only, with no country-code normalisation.
  - Merging duplicate profiles is not part of M4.

- **M5** (billing configuration) is complete. Migration 00014 adds the SQL function `seed_charge_codes` (the single definition of the ten standard charge codes): `CreateProperty` runs it through the `tenancy.Service.OnPropertyCreated` hook in its own transaction, and the migration backfills properties that existed before.
  - `internal/billingconfig` owns taxes, service charges, charge codes and the ordered rules, plus the `ChargeRuleResolver` (`ResolveRules`) that M6's calculation service reads. It computes no amounts.
  - `price_mode` and charge-type locks are the database triggers from migration 00010 (mapped to `PRICE_MODE_LOCKED`, `CHARGE_TYPE_LOCKED`); the service adds the clearer system-code and in-use checks.
  - Rule replacement deactivates then re-activates rows inside one transaction (the unique `(charge code, sequence)` index only covers active rows), and share-locks the mapped taxes so deactivation cannot race it.
  - sqlc now maps `numeric` to `decimal.Decimal` (nullable: `*decimal.Decimal`).
  - `POST {P}/charge-calculations` (the preview endpoint) belongs to M6.

- **M6** (Charge Calculation Engine) is complete; money and posting code may now build on it.
  - `internal/chargecalc` is pure (no database, clock or country knowledge): `Calculate`, `Validate` and `Verify`. Its tests are the worked examples of Step 7 plus property-based tests (fixed seeds, 30,000 random inputs each): an inclusive total always equals the quoted price, an exclusive net is base minus discount, negation symmetry, every component is exactly `round(base × rate)` of its own base, no amount exceeds the currency's decimals, the rounding adjustment stays within a few units of the smallest currency unit, and the result depends on the rules' sequence, not their list order. Mutation checks (bank rounding, unsigned discount, residual in tax, truncation, compounding) are each caught by these tests.
  - `billingconfig.Service.Calculate` is the `ChargeCalculationService`; `POST {P}/charge-calculations` previews it. The folio posting service (M9) and the reservation estimate (M8) must go through `Calculate`; nothing else multiplies by a rate.
  - The charge code screen has a calculator that previews the saved rules.

- **M7** (rate plans and rates) is complete. No migration: the tables exist in 00007.
  - `internal/rates` owns rate plans, the rate grid (bulk upsert by range, weekdays and room types) and the price lookup `NightlyPrices` that M8 uses to snapshot `reservation_room_rates`.
  - A plan that has rates cannot switch to a room charge code with another price mode (it would silently reprice the grid); this is enforced under a share lock on the plan, so a fill and a switch cannot interleave.
  - **Money precision (decided):** a property may use 0 to 3 currency decimals (IDR, USD, KWD). Migration 00015 widened every money column from `numeric(18,2)` to `numeric(18,3)` (keeping existing values exactly; its Down narrows and rounds, so only run it on data without a third decimal). The application rejects amounts with more decimals than the property's currency and amounts of 10^15 or more; API amounts are formatted with the currency's decimals.

- **M8** (availability and reservations) is complete. One migration, 00016 (`reservations.idempotency_key` and `idempotency_hash`, unique per property); the booking tables exist in 00008.
  - `internal/availability` is the inventory engine of 04-operations §14.1: `sellable` (active rooms minus active OOO/OOS blocks), `demand` (CONFIRMED lines by effective type plus open stays through tonight), `available = sellable - demand`. It also answers specific-room questions (`RoomIssues`: inactive, blocked, reserved, occupied) and lists free rooms. `rooms` uses it for the `INVENTORY_OVERSOLD` check.
  - `internal/reservations` implements create (draft, optionally confirmed at once), confirm, add and amend room, assign and unassign room, cancel (room or whole), reinstate, no-show, header edit, list and detail. Every mutation locks in the order business day (share) -> room types -> rooms -> reservation and lines, re-checks the `version`, bumps it, and audits. Sequences are taken last.
  - Nightly snapshots (`reservation_room_rates`) come from `rates.PriceNights`; overrides need `reservation.override_rate`. Estimates go through `billingconfig.Estimate`, which runs `chargecalc` per night.
  - **Decisions and deviations from 06-api.md §11-12:**
    - `POST {P}/reservations` needs the `Idempotency-Key` header. The key and a hash of the body are stored on the reservation: same key and body replays it, same key with another body is 422 `IDEMPOTENCY_KEY_REUSED`, and concurrent requests with one key converge on one reservation (unique index).
    - `unassign-room` takes the room type locks too (spec: `T[L4]` only): an upgraded line goes back to consuming its booked type, which must have the inventory.
    - Reinstate brings back only the rooms cancelled together with the reservation (same `cancelled_at`); a room cancelled on its own earlier stays cancelled. Cancelling clears the room assignment.
    - Cancel responses are `{reservation, folio_balance, requires_folio_resolution}`. The folio fields are computed from `folios` and `folio_items` (empty until M9).
    - Availability search lists a plan with incomplete grid as `missing_nights` and no estimate instead of failing.
    - The tape chart has its own read-only endpoint `GET {P}/tape-chart?from&to` (at most 62 days); the spec only named the screen. Checked-in lines are drawn from their stay segments (M12), so moves, extensions and early departures show.
    - Deposits (`POST .../deposits`) belong to M9 with the payment service.

- **M9** (folio core and payments) is complete. One migration, 00017: `approved_by` on `folio_items` and `payments`, with CHECKs (`folio_items_approval_ck`: ADJUSTMENT and REVERSAL items carry an approver and no other item does; `payments_approval_ck`: REFUND and VOIDED payments carry one and no other payment does) and the payments guard now lets `approved_by` change with POSTED -> VOIDED. The new permission is `correction.approve`.
  - `internal/iam/approval.go`: `Service.VerifyApproval` checks the approver's email and password with the login verifier and login rate limits (same limiters, an `approval|tenant|email` key), then `correction.approve` at the property (tenant administrators hold it everywhere). It returns an `iam.Approval` whose only constructor is that function, so posting code that takes an `Approval` knows a password was checked. Errors: 422 `APPROVAL_REQUIRED`, 401 `APPROVAL_INVALID_CREDENTIALS` (one generic error), 403 `APPROVAL_NOT_PERMITTED`, 429 `TOO_MANY_ATTEMPTS`. The password is never stored, audited or echoed (a test greps the audit log for it).
  - `internal/folios`: `posting.go` is `FolioPostingService` and the only writer of `folio_items` and components (charge, adjustment, payment and refund entries, reversal). `payments.go` is `PaymentService` (post, deposit, void, refund, cashier list). `charges.go` holds the charge, adjustment and reversal use cases. Every posting bumps `folios.version`, so a stale "close" is rejected.
  - **Decisions and deviations:**
    - The approval is verified **before** the transaction opens, not inside it (06-api.md §14.1 said inside): no lock is held while argon2 runs. A replay (same `Idempotency-Key`) is answered before the approval is checked.
    - Charges, adjustments, payments, deposits and refunds need `Idempotency-Key` (400 `IDEMPOTENCY_KEY_REQUIRED`). The key is stored on the item or payment; a replay returns the stored result, a key reused on another folio is 422 `IDEMPOTENCY_KEY_REUSED`, concurrent requests with one key converge on one row.
    - Manual charges refuse ROOM codes (409 `ROOM_CHARGE_REQUIRES_ROOM_POSTING`); adjustments may use them. Room postings arrive with M11.
    - A closed folio takes no postings (409 `FOLIO_CLOSED`); `folio.post_after_checkout` and `folio.reopen` are not used yet.
    - A payment is voided (same business date, no refunds, POSTED, PAYMENT type) with its ledger entry reversed and the payment marked VOIDED; an earlier date is refunded instead. Refunds check `amount <= original - refunds` under the original payment's row lock. A refund leaves by a method the property allows (`properties.refund_methods`, cash only by default; migration 00035), which may differ from the method of the payment (a bank transfer refunded in cash).
    - The reversal of a room-charge item flips its `stay_charge_postings` row to REVERSED (tested with a seeded register row).
    - A deposit locks the reservation, then finds or creates its open folio without a stay; the new folio is not locked again after its number is taken (lock order).
    - Payment lists: `GET {P}/payments?business_date&method` returns net totals per method only when `business_date` is given, voided payments excluded.
  - The frontend has the folio screen (items, components, balance, charge and payment forms), the shared Approval dialog (the approver's password lives only in the dialog and is cleared once handed over), the cashier screen, a folio list, and a deposit form on the reservation.

- **M10** (check-in and walk-in) is complete. One migration, 00018 (`stays.idempotency_key`, unique per property); the stay tables exist in 00009.
  - `internal/frontdesk` implements check-in (`CheckInService`), walk-in (`WalkInService`), reverse check-in, the stay list and detail, and an arrivals list. `reservations` gained the door front desk uses to change its rows (`Lock`, `MarkCheckedIn`, `MarkCheckInReversed`, `CreateHeld`) and `folios` gained the stay folio hooks (`LockUnlinkedFolio`, `AttachStayFolio`, `DetachStayFolio`, `StayFolios`), so each module stays the only writer of its tables.
  - Check-in rules (04-operations §14.3): the line and header are CONFIRMED and the arrival is the business date; the room is active, not blocked and not occupied for `[BD, departure)` and not held by another confirmed line; CLEAN or INSPECTED (INSPECTED only when the property requires an inspection), with an override that needs `frontdesk.checkin_unready_room` and a reason; the party fits the room type of the room. A room of another type than the one the line consumes is an upgrade (needs `reservation.upgrade` and the room type's inventory). Effects: the stay (OPEN), its open segment, accompanying guests, the folio (the reservation's open deposit folio is linked, otherwise one is created), the line CHECKED_IN and one audit entry. Nothing else is written.
  - Lock order for check-in: business day, room types, rooms, reservation and lines, the deposit folio, then the stay and folio numbers. Walk-in takes the room type and room locks itself before creating a new guest (a guest code is a sequence number), then calls `reservations.CreateHeld` (create, confirm and assign under those locks) and the same check-in core. Reverse check-in marks the room DIRTY before it locks the room, because `housekeeping.MarkDirty` re-enters the business day.
  - **Decisions and deviations from 06-api.md §13:**
    - `Idempotency-Key` is stored on the stay, so a double click or retry returns the stay it created, and concurrent requests with one key converge on one stay; a losing request that fails with a version conflict looks the key up once more.
    - Walk-in answers `{reservation: {id, confirmation_number, status, version}, stay, stay_room, folio}`; the full reservation is one `GET` away.
    - Reverse check-in is refused after the arrival day or after a room move (`CHECK_IN_NOT_REVERSIBLE`), once a CHARGE is posted to the stay's folio (`CHECK_IN_HAS_CHARGES`), and always needs a reason; the room line goes back to CONFIRMED and keeps its room.
    - `GET {P}/arrivals?date` is new (the arrivals screen needs rooms, not reservations); `GET {P}/stays/{id}` shows `posted: false` for every night until room charges exist (M11), and has no `expected_charges` yet.
    - Move, extend, shorten, add guest and check-out are M12 (below).
  - The frontend has the arrivals list with the check-in panel (free rooms with housekeeping status, upgrade note, not-ready override), the walk-in screen, the in-house list, the stay detail with reverse check-in, and the room status board.

- **M11** (expected charges and room charge posting) is complete. No migration: `stay_charge_postings` and its partial unique index exist in 00010.
  - `internal/expected` is the Expected Charge Engine: a `Loader` (read-only SQL snapshot of stays, segments, the nightly price snapshot, POSTED register rows and open folios) and a pure `Evaluate(Snapshot, Scope)` applying the eight rules of §8.3 in order, plus `FindInvalid` (posted nights outside the stay's nights, or of a cancelled stay). The evaluator has unit tests for every rule, the rule order, room moves (on the business date and on the arrival day) and the scope.
  - `internal/roomcharge` is `RoomChargePostingService`. A real run takes the business day share lock, locks the stays FOR UPDATE in id order, evaluates after the locks, locks the folios in id order, then posts each READY night in order of stay and night and writes its register row; it audits one summary entry. A dry run (the preview) only reads and calls the charge calculation service. A second run answers ALREADY_POSTED; after a reversal flips the register row to REVERSED the night is READY again. `Post` is the method night audit (M13) and check-out (M12) will call, with their own trigger.
  - **Only one code path posts room revenue:** `folios.RoomPoster` is a capability object (`Service.RoomPoster()`), handed only to the room charge service in `internal/app`. It posts a CHARGE on a ROOM charge code, stamped with the stay segment of the night and source `ROOM_POSTING`; manual charges still refuse ROOM codes, and the poster refuses non-ROOM codes.
  - **Decisions and deviations from 06-api.md §15:**
    - The two endpoints are `POST {P}/night-audit/room-charges/preview` and `POST {P}/night-audit/room-charges`; either `nightaudit.run` or `folio.post_charge` is enough. The `Idempotency-Key` header is required on posting for the contract, but the run is idempotent by itself (the register), so the key is not stored.
    - The business date in the request must equal the open one (409 `BUSINESS_DATE_MISMATCH`). An explicit `stay_ids` that does not exist is 404 `STAY_NOT_FOUND`.
    - The night's ledger item carries the service date of the night and the business date of the posting, so a night caught up later keeps its own service date.
    - The `revalidation` of a posting answer is read after the commit: `ready`, `errors` (ERROR nights as items) and `invalid` (posted nights that should not exist).
  - The frontend has the "Room charges" screen: the preview table (missing nights marked), totals, problems, and "Post room charges".

- **M12** (stay changes and check-out) is complete. No migration: it uses the stay, segment, reservation and folio tables.
  - `internal/frontdesk` gained `Move` (RoomMoveService), `ChangeDeparture` (StayChangeService), `AddGuest` and `CheckOut` (CheckOutService). `reservations` gained `ExtendNights`, `TrimNights`, `OverrideNights` and `MarkCompleted`; `folios` gained `CloseStayFolios`; `availability.RoomIssuesFor` can exclude the stay being extended; `housekeeping.MarkDirtyLocked` marks a room DIRTY from a caller that already holds the business day and room locks; `roomcharge.PostLocked` is `Post` for a caller past L1.
  - Lock order (05-transactions-locking rows 4 and 7): business day, room types, rooms (the old room is marked DIRTY here), the stay, the folios. Check-out locks the room, then the stay, then posts (stays and folios again at the same levels) and closes the folios, all in one transaction: a folio that is not balanced rolls the tonight room charge back too.
  - **Room move** needs `frontdesk.room_move` (`frontdesk.rate_change` for `new_nightly_rates`, which may only touch uncharged nights). The target must be free for `[BD, max(departure, BD+1))`, have inventory if its type differs, and be CLEAN (INSPECTED when the property requires it; override needs `frontdesk.checkin_unready_room`). The open segment is closed, a new one opened; the old room becomes DIRTY (housekeeping log source ROOM_MOVE). Tonight's room charge follows the segment that covers the night.
  - **Change departure** needs `reservation.update`. Extending needs the room free for the extra nights (409 `ROOM_NOT_AVAILABLE_FOR_EXTENSION` with `alternative_rooms` and `suggest_room_move`) and inventory; the new nights are priced from the grid or `nightly_overrides`. Shortening needs a date after the business date and after the last charged night (409 `NIGHT_ALREADY_POSTED`). The reservation line keeps its own dates; the stay's are the truth for demand.
  - **Check-out** needs `frontdesk.checkout`. It posts every unposted night up to the business date with trigger CHECK_OUT, requires a zero balance on every folio of the stay (409 `FOLIO_NOT_BALANCED`, context `folios`), closes them, closes the segment, completes the room line (display status CHECKED_OUT) and makes the room DIRTY (occupancy VACANT is derived). Early departure needs `confirm_early_departure` (409 `EARLY_DEPARTURE_NOT_CONFIRMED`). A night that cannot be posted refuses the check-out (409 `REQUIRED_CHARGES_NOT_POSTED`).
  - **Decisions and deviations from 06-api.md §14:**
    - Check-out after midnight (the calendar date passed the business date, the audit has not run): the guest still owes the night of the business date and the stay ends the next day; before midnight a guest leaving today ends the stay today. A same-day arrival and departure is charged one night (there is no day use).
    - `Idempotency-Key` is required on check-out but not stored: a retry with the same stay version of a completed check-out returns its result; other versions are 409.
    - `GET {P}/stays` gained `departure_until` for the departures list.
    - `change-departure` is open to `reservation.update`; add guest to `frontdesk.checkin`.
  - The frontend has the departures list, the check-out wizard (early-departure confirmation, unbalanced folio links, result summary), and on the stay detail the room move, extend/shorten and add-guest dialogs.

- **Accounting readiness** (migration 00019, between M12 and M13). The PMS has no chart of accounts, but its codes can be linked to one without a later data migration.
  - **Codes, not ids.** `charge_codes.gl_account_code` (revenue), `taxes.gl_account_code` (tax payable) and `service_charges.gl_account_code` (service charge payable) are optional text account codes (`4-1100`, `2.1.05`, `REV:ROOM`; A-Z 0-9 `. - _ : /`, at most 30, upper-cased, checked by a CHECK constraint). There is no foreign key: the accounting module will own the COA and validate the codes against it. Configuration is on the charge-code, tax and service-charge screens and API (`gl_account_code`; an empty string clears it; audited like any other change).
  - **The ledger carries the account it was posted with.** `folio_items.revenue_account_code` and `folio_item_components.gl_account_code` are filled in the same INSERT that writes the item (a subselect of the mapping in force at that moment), so every room night, manual charge, adjustment, tax and service component is reproducible by account. A later remapping never rewrites history (the ledger is append-only), and a reversal copies the codes of the item and components it reverses, even when the original was unmapped. Payments are not revenue and carry none.
  - **Reading the ledger by account.** Revenue of an account is `sum(net_amount)` over `folio_items.revenue_account_code` (net includes the rounding adjustment); service and tax liabilities are `sum(amount)` over components grouped by `gl_account_code` and `component_type`. For every item `debit - credit = net_amount + service_charge_total + tax_total`, which is the balancing identity for a journal (guest ledger debit against the credits above). Both are exposed on the folio API (`revenue_account_code`, `components[].gl_account_code`), so an accounting module or export needs no new engine.
  - **Not mapped yet, on purpose:** payment methods (cash, card, bank), the guest ledger / deposit liability and city-ledger accounts, and rounding. They are accounting-side decisions (they depend on its COA and journal rules); the owner of the accounting module adds those mappings, with the same code-based approach, when it is built. Posting is never blocked by a missing mapping.

- **M13** (night audit) is complete. No migration: the summary is stored in `business_days.summary`.
  - `internal/nightaudit` is `NightAuditService`, an orchestrator with no posting or calculation code. `Preview` runs the checks (unresolved arrivals, unresolved departures, room charges in ERROR, invalid postings) and a dry run of the room charges, plus warnings (stale drafts, open folios with a balance on reservations without a live room, blocks ending today). `NoShows` is the bulk action; `Run` is the orchestration. Checks are plain queries in `queries.sql`; posting is `roomcharge.PostLocked`, housekeeping is `housekeeping.MarkDirtyLocked`, the date moves through `tenancy.CloseAndOpenNextLocked`.
  - **`Run` is one transaction** in this order: advisory lock `night_audit:{property}` (409 `NIGHT_AUDIT_IN_PROGRESS`, fail fast), the OPEN day FOR UPDATE (409 `BUSINESS_DATE_MISMATCH`), the time guard (409 `NIGHT_AUDIT_TOO_EARLY`), the checks (409 `NIGHT_AUDIT_BLOCKED`, `context.blockers` in the preview's shape), housekeeping (when `night_audit_marks_occupied_dirty`, rooms with an open segment become DIRTY, source NIGHT_AUDIT), the room charges (trigger NIGHT_AUDIT, missing nights included), a revalidation (no READY, ERROR or invalid item may remain), the closing summary, `CloseAndOpenNext`, and the audit entry. Everything rolls back on any blocker. Because the day is held FOR UPDATE, every writer (they take it FOR SHARE) waits, so a racing payment lands on exactly one business day.
  - **Lock order:** L0 advisory, L1 day, L3 rooms, L4 stays then folios. Housekeeping runs before the posting, not after as the step list reads: the housekeeping row is an L3 lock and may not be taken after the L4 stays; since the whole run is atomic the order has no visible effect.
  - **Bulk no-show** (`reservations.BulkNoShow`, `nightaudit.no_show`): the request names the exact `reservation_room_ids` and `confirm: true`; the reservations and lines are locked in id order; if any id is missing, no longer CONFIRMED or not due, nothing changes (409 `NO_SHOW_SET_CHANGED`, `context.changed`). The server never expands the set. It audits each line, bumps each reservation once, and answers with the blockers that remain.
  - **Closing summary** (`summary` jsonb of the closed day): rooms {total, out_of_order, out_of_service, sellable, occupied, sold}, arrivals (stays that arrived on the date), departures (checked-out stays whose last segment ended on it), no-shows (audit entries of the date), room revenue {net, service, tax}, revenue by charge type, payments by method (payments, refunds, net; voided excluded), occupancy % (occupied / (total − OOO)), ADR (room net / room nights charged), RevPAR (room net / (total − OOO)), room charges posted. Money uses the property's decimals.
  - **Decisions and deviations from 06-api.md §15:** the `room-charges` preview and post endpoints belong to M11 and are unchanged; the run needs no idempotency key (a second request fails with `BUSINESS_DATE_MISMATCH`); `GET /night-audit/preview` adds `night_audit_allowed_from`; an unresolved departure is a stay with `departure_date ≤ BD` (a guest due out today must be checked out or extended before the audit); the no-show answer's `marked` lists reservation room, reservation and confirmation number.
  - The frontend has the "Night audit" wizard: time guard, unresolved arrivals (select, confirm, mark as no-show), unresolved departures and charge errors with links to the stay, room charge counts, warnings, and the confirmed run with the closing summary; the header clock refreshes to the new business date.

- **M14** (reports) is complete. No migration and no database views: the reports are plain read-only queries (`internal/reports`), no locks, no writes. A new permission `report.view` (catalogue group "Reports") guards all of them.
  - **Reports** under `{P}/reports/`: `daily-summary?date`, `revenue?from&to`, `tax?from&to`, `cashier?from&to`, `statistics?from&to`, `arrivals?date`, `departures?date`, `in-house`. Every one answers JSON, or CSV with `?format=csv`. Ranges are business dates, at most 366 days (422 otherwise).
  - **Money comes from the ledger snapshots, never the masters.** Revenue sums `folio_items` (charges, adjustments, reversals, signed) by business date and charge code and revenue account code; the tax report sums `folio_item_components` grouped by the posted code, name, rate and account, so a rate edited in the range gives two lines and the past never moves; the cashier report sums `payments` by business date and method (refunds netted, voided apart). - **Documents and e-mail** (after M15; migration 00021). Printed documents and the confirmation e-mail.

The rendering takes plain data and is deterministic; the service assembles the data through the owning services, so each document needs the permissions of what it shows: invoices and receipts `folio.read` plus `reservation.read` (they name the reservation and the guest), the card and the confirmation `reservation.read`; the guest's profile fields (address, ID, nationality) appear only for callers with `guest.read`, otherwise they print as a dash to be written in. Responses are `application/pdf`, `inline`, `Cache-Control: no-store`, `nosniff`.

Amounts use the property's decimals with thousands separators; dates print as `30 Sep 2026`.

  - **Confirmation e-mail** (`internal/notifications`): confirming a reservation (create with `confirm`, or `Confirm`) queues an e-mail to the booker in the **same transaction** (`email_outbox`, audited as `email.queued`), so it is never lost and a mail server that is slow or down never blocks or fails a booking. A background worker (`App.Background`, every 15 s) claims due rows with `FOR UPDATE SKIP LOCKED` and a 10-minute lease (two workers never send one message twice), renders the message (text and HTML, with the confirmation PDF attached) and sends it. A transient failure is retried after 1 min, 5 min, 30 min and 2 h; the fifth failure, or a permanent refusal (a 5xx for the recipient, an invalid address), marks the row FAILED; a confirmation for a reservation that is no longer confirmed is SKIPPED. Rows are `QUEUED | SENT | FAILED | SKIPPED` with `attempts` and `last_error`.

Settings: `PMS_SMTP_HOST`, `PMS_SMTP_PORT` (587), `PMS_SMTP_TLS` (`starttls`, `tls` or `none`), `PMS_SMTP_USERNAME`, `PMS_SMTP_PASSWORD`, `PMS_SMTP_FROM` (a plain address, required with a host), `PMS_SMTP_FROM_NAME`. Credentials over an unencrypted connection are refused in production. Header values cannot carry a line break, so a hostile subject or name cannot inject headers.

- **Corporate accounts, groups and the city ledger** (after M15; migration 00022). Companies, booking groups and receivables.
  - **Companies** (`internal/companies`, `company.manage`; readable with `reservation.read` or `cityledger.read`): a corporate account per property with a code, contacts, tax ID, payment terms and a **credit limit** (`null` = no limit, `0` = no credit). A company that still owes money cannot be deactivated (409 `COMPANY_HAS_BALANCE`). A reservation names the company that is billed (`reservations.company_id`).
  - **Booking groups** (`internal/groups`, `group.manage`): a block of reservations that share dates and optionally a company (conference, tour, wedding). Rooms are booked as **ordinary reservations that name the group** (`booking_group_id` on create or header patch), so the booking engine, locks and idempotency are unchanged; the stay must lie inside the group's dates (422 `OUTSIDE_GROUP_DATES`), an inactive group takes no rooms (409 `GROUP_INACTIVE`) and the reservation inherits the group's company. A group's dates cannot shrink past a booked room and its company cannot change while reservations bill another (409 `GROUP_HAS_ROOMS_OUTSIDE_DATES`, `GROUP_HAS_RESERVATIONS`). Cancelling a whole group at once is not offered (it would chain reservation locks against the global order): cancel its reservations one by one.
  - **City ledger** (`internal/cityledger`, `cityledger.read` / `cityledger.transfer` / `cityledger.receive`): a company's balance is **derived** (posted `CITY_LEDGER` payments of the company minus posted receipts), never stored. `POST {P}/folios/{id}/city-ledger-transfers` posts a payment with method `CITY_LEDGER` and a `company_id`: it credits the open folio (so the folio can be settled and closed) and adds to what the company owes. It cannot exceed the folio's balance (409 `TRANSFER_EXCEEDS_BALANCE`) or take the company above its limit (409 `CREDIT_LIMIT_EXCEEDED`). `CITY_LEDGER` is not a way to pay: the payment, deposit and refund endpoints refuse it, and a transfer is never refunded; it can be voided (with approval) on its business date unless receipts already settled it (409 `COMPANY_BALANCE_SETTLED`).
  - **Receipts** (`city_ledger_receipts`, number series `CLR`): money a company pays against its account (`POST {P}/city-ledger/accounts/{id}/receipts`, Idempotency-Key), capped at what it owes (409 `RECEIPT_EXCEEDS_BALANCE`). Append-only like payments (POSTED to VOIDED only; void needs an approval and the same business date).
  - **Locking:** the company row is lock level 44 (after payments, before sequences), so the credit limit and the receipt cap hold under concurrent transfers and receipts; a group is level 45, share-locked while a reservation joins it and locked for update while it is edited. See [05-transactions-locking.md](05-transactions-locking.md).
  - **Reports:** `GET {P}/city-ledger/accounts` (`owing`, `q`), `.../accounts/{id}`, `/statement` (from/to, running balance, opening balance), `/aging` (0-30, 31-60, 61-90, 90+ days, receipts settle the oldest transfer first, as of the business date) and `GET {P}/companies/{id}/statement.pdf`. The cashier report counts receipts as money received and leaves transfers out of its net; the night audit summary has a `city_ledger` block (transferred, received, outstanding) and its `payments_by_method` is the till (receipts in, transfers out).
  - **Invoices to a company** (migration 00023, permission `cityledger.invoice`, number series `CINV`): an invoice **combines several transfers of one company** into one billing document. Only a transfer whose **guest has checked out** (the stay behind the folio is CHECKED_OUT) can be invoiced; transfers of guests still in house are listed as candidates but disabled. A transfer is on at most one live invoice (partial unique index on the lines); voiding an invoice (with approval) releases its transfers so they can be invoiced again. The due date is the invoice date plus the company's payment terms. An invoice does **not** change what the company owes (that stays transfers minus receipts) and receipts are not allocated to invoices; invoices and their lines are append-only (ISSUED to VOIDED, a line can only be released). Creating or voiding one locks the company row (level 44), so two invoices cannot claim the same transfer. `GET {P}/city-ledger/accounts/{id}/invoice-candidates`, `GET/POST {P}/city-ledger/accounts/{id}/invoices`, `GET {P}/city-ledger/invoices/{id}`, `POST {P}/city-ledger/invoices/{id}/void`, `GET {P}/city-ledger/invoices/{id}/invoice.pdf` (one line per checked-out stay: check-out date, guest, room, stay dates, folio, reference, amount; a voided invoice is stamped VOID). Errors: 409 `TRANSFER_NOT_AVAILABLE`, `STAY_NOT_CHECKED_OUT` (both with `context.payment_ids`), `INVOICE_ALREADY_VOIDED`. Frontend: "New invoice" (tick the transfers) and "Invoices" (print, void) on the company account screen. Not done, on purpose: adding transfers to an invoice that was already issued (void it and issue a new one), allocating receipts to invoices, and e-mailing invoices.
  - **Paying invoices** (migration 00024): a receipt can carry `allocations` (`{invoice_id, amount}`) that pay issued invoices of the same company; the part not allocated stays on account. What an invoice has been paid is **derived** (allocations of posted receipts): `paid`, `outstanding` and `payment_status` (UNPAID, PARTIAL, PAID, VOID) are on every invoice, so voiding a receipt reopens its invoices. An invoice cannot be paid more than it owes (409 `ALLOCATION_EXCEEDS_INVOICE`), a voided invoice takes nothing (409 `INVOICE_NOT_PAYABLE`), and an invoice with posted payments cannot be voided (409 `INVOICE_HAS_PAYMENTS`). The DB ties a receipt and an invoice to the same company (composite FKs) and allocations are append-only. The company lock keeps concurrent receipts from over-paying an invoice. The invoice PDF shows total, paid and balance due. Frontend: **Pay** on an invoice of the company account screen. Not done: automatic allocation (oldest invoice first), credit notes and write-offs.
  - **Frontend:** Setup → Companies, Groups (list, detail with its reservations and "Add rooms"), City ledger (accounts, account detail with aging, statement, "Print statement", receive and void a receipt), "Transfer to a company" on an open folio, company and group on the booking screen and the reservation.
  - **Not done, on purpose:** a master folio shared by a group (each guest keeps a folio that is transferred to the company), group-wide cancel, rooming-list import, dunning, interest and write-offs, and a general ledger posting (the account codes of 00019 are the hook).

  - **The cleaning list** (`housekeeping_tasks`, permission `housekeeping.assign`): `POST {P}/housekeeping/tasks/generate` builds the list of the current business date from stays and reservations: occupied rooms get CHECKOUT (the guest leaves today or is overdue) or STAYOVER, a vacant room that is not clean gets ARRIVAL (a guest is assigned to it today) or DIRTY; arrivals and HIGH rooms get high priority; a room under a block gets nothing and a room that already has a task that day gets no second kind. Running it again adds only what is new (unique index on AUTO tasks), so it can be run through the day, also by two people at once. Supervisors can add MANUAL tasks (DEEP, OTHER and the rest).

Starting a task (assigns it to the starter when it has no owner) moves a DIRTY room to CLEANING; finishing it moves a DIRTY or CLEANING room to CLEAN and never to INSPECTED (that stays an inspector's call); skipping needs a reason (for example DND) and leaves the room alone. These use the normal status machine, so each change is in the room's log and audit trail. Reporting and reading need `maintenance.report` (give it to housekeepers); everything that changes a request needs `maintenance.manage`. **Blocking the room:** `POST .../maintenance-requests/{id}/block` creates an OOO or OOS room block through the room service (so the usual conflict checks apply, and `room_block.manage` is needed too), links it to the request, and a failed block changes nothing; resolving or cancelling with `release_block` cancels it again. - **Accounting: the chart of accounts** (after M15; migration 00028, `internal/accounting`, permissions `accounting.view`, `accounting.manage`, `accounting.post`, `accounting.close`). The general ledger comes in steps; this is the first.
  - **USALI chart per property:** every property gets a standard chart of about 200 accounts laid out after the Uniform System of Accounts for the Lodging Industry, seeded when it is created (and for the properties that existed): balance sheet accounts (cash and clearing accounts, guest ledger, city ledger, inventories, prepaid, property and equipment with accumulated depreciation, payables, accruals, advance deposits, taxes and service charges payable, long-term debt, equity), operating revenue by department (rooms, food and beverage, other operated departments, rentals and other income, miscellaneous income), departmental expenses, undistributed operating expenses (administrative and general, IT, sales and marketing, property operations and maintenance, utilities), management fees, and the non-operating items (rent, property taxes, insurance, depreciation, interest, income taxes). Codes are 4-digit numbers (1 assets, 2 liabilities, 3 equity, 4 revenue, 5 to 7 expenses). The single definition is the SQL function `usali_chart()`; `seed_chart_of_accounts` is idempotent.
  - **Account rules:** header accounts only group, an account that takes postings needs a `statement_group` of its type (what the balance sheet and the USALI income statement add up), the parent is a header of the same type and nothing sits under itself. The code, type and normal side never change; a contra account (accumulated depreciation, allowances, owner drawings, interest income) carries the other side. An account cannot be deleted or turned off while something refers to it: children, the system map, a charge code, tax or service charge that carries its code.
  - **System accounts (`gl_account_map`):** ten keys the day close posts to: CASH, CARD, BANK_TRANSFER and OTHER_PAYMENT (what a payment method is received into), CITY_LEDGER and GUEST_LEDGER (the receivables), ADVANCE_DEPOSITS (deposits are a liability until the guest checks out), TAX_PAYABLE and SERVICE_PAYABLE (a tax or service charge with no account of its own) and SUSPENSE (anything that cannot be placed). The seed gives each its default, and the standard charge codes their revenue accounts (ROOM to 4110, RESTAURANT to 4210, MINIBAR to 4230, and so on).
  - **Charge codes, taxes and service charges** still carry their account code as text (`gl_account_code`, migration 00019); the chart validates them softly: `GET .../accounting/unmapped` lists the active ones whose code is empty, unknown, inactive, a header or of the wrong type, and says where their amounts will be posted instead. Nothing blocks a day close because of configuration.
  - **CSV:** `GET .../accounting/accounts?format=csv` exports the chart; `POST .../accounting/accounts/import` adds and updates accounts by code (all or nothing, `dry_run` to check a file first, parents may appear after their children).
  - **Locking:** each property's `accounting_settings` row is lock level 46 (after companies and groups, before sequences): editing the chart, the system accounts or a period takes it FOR UPDATE, posting a journal will take it FOR SHARE, so the chart cannot change under a journal and two people cannot put two accounts under each other.
  - **Frontend:** Accounting → Chart of accounts (tree, filters, add, edit, delete, import and export) and System accounts (the ten keys, and what is not mapped).
  - **Account code hints:** the account code field of charge codes, taxes and service charges suggests the accounts of the chart that fit (revenue, liability) and says what the typed code is, or where the amounts go instead (suspense, tax payable, service payable) when it is unknown, inactive, a header or of the wrong type. It is a plain input without `accounting.view`.
- **Accounting: journals and periods** (migration 00029; the second step of the general ledger). The books are written from the guest ledger when a business day closes.
  - **One journal per business day (`DAY_CLOSE`):** the night audit calls `accounting.PostDay` inside its own transaction, after the room charges and before the day closes, so a day cannot close without its journal (a property without accounting settings, or a date before its start date, is skipped). The journal is derived from the folio ledger of that date with detail per account and source: charges debit the **guest ledger** (by charge code) against the revenue account the item carried when it was posted (net), and the tax and service charge accounts of its components; a payment debits the account of its method (cash, card, bank, other, or the **city ledger** for a transfer) against the guest ledger; city ledger receipts debit the method's account against the city ledger. Reversals, voids and refunds follow the item or payment they undo. What cannot be placed (no code, unknown, inactive, header or wrong type) goes to TAX_PAYABLE, SERVICE_PAYABLE or SUSPENSE, so a close never fails on configuration. A day with nothing to post is recorded in `gl_day_posts` without a journal.
  - **Deposits are a liability until checkout:** a payment that is not on the city ledger and was taken before the guest checked in (or while the stay has no folio) is credited to ADVANCE_DEPOSITS instead of the guest ledger; refunds and reversals are judged by the payment they belong to (view `folio_item_gl`). When the folio closes (`folios.closed_on`, set from the open business day), the day close moves what it held from ADVANCE_DEPOSITS to the guest ledger, per folio. So the guest ledger account always equals what open folios owe plus the deposits they hold.
  - **Backfill:** `POST .../accounting/journals/post-pending` (accounting.close) journals the closed days that have none, oldest first, at most 400 a call, one at a time under the settings lock. Set the accounting start date to the first business date so the whole history is journaled.
  - **Manual journals and reversals:** accounting.post, Idempotency-Key, at least two lines, each a debit or a credit at the property's decimals, debits equal credits (checked again by a deferred trigger at commit); the date is between the start date and the current business date, in an open month; the guest ledger, city ledger and advance deposits accounts are refused (only the day close writes them). A manual journal is reversed once, with an approval; day close journals are corrected in the folios.
  - **Periods:** calendar months. A month closes (accounting.close) in order, after it has ended, when every business day of it is closed with its journal; a closed month takes no journals or reversals dated in it. Only the latest closed month reopens, with a reason.
  - `gl_journals`, `gl_journal_lines` and `gl_day_posts` are append-only (no update, delete or truncate); a journal number comes from the JOURNAL sequence (prefix JV). The lock order gains the settings row at level 46, taken in share mode by posting and in update mode by the backfill and the period operations.
  - **Not yet:** trial balance, general ledger, income statement (USALI), balance sheet and their exports come next. There is no year-end closing entry: the balance sheet will compute current-year earnings.
  - **Frontend:** Accounting → Journals (filters, lines of a journal, manual journal form with a live balance, reversal with approval, "Journal missing days") and Periods.
- **Accounting: ledgers, statements and reconciliation** (the third step of the general ledger; read-only, from the journals; permission `accounting.view`).
  - **Trial balance** (range): every account with entries up to the end date, with its opening balance, the movement of the range and the closing balance, each on the side it falls on; debits equal credits in every column.
  - **General ledger** (one account, range): the entries with a running balance on the account's normal side, the source of each day close line (charge code, tax, payment method, receipts, deposit release) and an opening balance; at most 5000 lines.
  - **Income statement after USALI** (range): operating revenue by department (rooms, food and beverage, other operated, rentals and other, miscellaneous), departmental expenses and profit, undistributed operating expenses, **GOP**, management fees, non-operating expenses (**EBITDA**), depreciation (EBIT), interest, income taxes, net income. It adds up the `statement_group` of each account; a contra account reduces its group.
  - **Balance sheet** (as of a date): assets, liabilities and equity by group; equity includes the earnings of all periods to date (there is no year-end closing entry), and `difference` shows if the books ever fail to balance.
  - **Control accounts**: the guest ledger, advance deposits and city ledger accounts against what the folios and the city ledger say as of a date: folio items to the date plus the deposits held on folios not closed by then; deposits held; transfers to companies less receipts. Closed days without a journal (`pending_days`) and the open business day (`includes_open_day`) are reported, since they make the books fall behind. Folio activity from before the accounting start date is not in the books.
  - Trial balance, ledger, income statement and balance sheet export as CSV (`format=csv`).
  - **PDF:** the trial balance, a general ledger, the income statement (USALI) and the balance sheet are also documents (`.../accounting/trial-balance.pdf`, `accounts/{id}/ledger.pdf`, `income-statement.pdf`, `balance-sheet.pdf`) with the hotel letterhead, the same parameters as the reports and the permission `accounting.view`; a balance sheet that does not balance prints a warning. Buttons on each report screen.
  - **Frontend:** Accounting → Trial balance, General ledger, Income statement, Balance sheet, Control accounts.
- **Accounting: year-end closing** (migration 00030; accounting.close).
  - **Fiscal years** start on the first day of `fiscal_year_start_month` (a year is labelled FY plus the year it ends in) and are listed from the accounting start date with their result (net income from the journals, closing journals left out), the months closed and whether they can be closed.
  - **Closing a year** needs it to have ended, the year before it to be closed and every month of it closed (Periods). The **closing journal** (type CLOSING, dated the last day of the year) debits and credits every revenue and expense account with a balance in the year back to zero and puts the result on the new system account **RETAINED_EARNINGS** (default 3200, the eleventh key of the system accounts). A year with no result closes without a journal. The income statement leaves closing journals (`gl_journals.is_closing`) out, so a closed year still reports its result; the balance sheet and the ledgers keep them, so the next year's "earnings to date" start from zero and equity shows retained earnings.

Voiding a bill (approval) is only possible without payments and reverses its journal on the current business date.

Only the payables post to ACCOUNTS PAYABLE: manual journals refuse it (as they refuse the guest ledger, city ledger and advance deposits). Journals of a bill or payment are not reversed by hand.

- **Bank reconciliation** (migration 00032, `internal/bankrec`; permissions `bank.view`, `bank.manage`, `bank.reconcile`). The cash and bank accounts of the books are proved against the statements of the bank.
  - **Bank accounts:** an active asset account that takes postings is registered once (`bank_accounts`), with a name and the account number at the bank.
  - **Statements:** imported per bank account and period as CSV (a header names the columns in any order: date, description, reference, and `amount` with money in positive, or credit/debit columns; dates as YYYY-MM-DD or DD/MM/YYYY; a BOM and thousands separators are tolerated). The whole file is checked first and a mistake changes nothing (a field error per row): the lines lie in the period and add up to the difference of the printed balances, the opening balance is the closing balance of the statement before, and statements do not overlap and are imported in the order of their periods. An open statement can be deleted.
  - **Clearing:** a statement line is matched with one or more journal lines of the account (`bank_clearings`: a journal line is cleared up to its amount, in one clearing or in **parts** by several statement lines; the journal lines themselves never change). Automatic matching takes each unmatched line with the one journal line of the same amount left on it, dated within three days (the nearest, when it is the only nearest); a journal line that carries the **reference** of the statement line (the transfer reference the guest gave) beats one that does not and may be up to 14 days away. The rest is left for a person. Journal lines can be cleared without a statement line only when they offset each other (a payment and its reversal), or, in the first statement of an account, when they are from before it (the opening balance).
  - **What the bank shows and the books lack** (a fee, interest): posted from the statement line (`bank.reconcile`): a **BANK journal** dated the day of the line, the bank account against the account chosen, cleared against the line at once. The date must be in an open accounting period; the journal goes through `accounting.Poster`, like the payables.
  - **Reconciling:** a statement is reconciled when the statement before it is, every line is matched, and the journal lines cleared so far (this statement and the earlier ones) add up to the closing balance of the bank. The comparison is shown as in a reconciliation report: closing balance, plus money in transit (journal lines the bank does not show yet), less outstanding payments, equals the book balance. A reconciled statement is final (the database refuses changes to its lines and clearings); the latest reconciled statement of an account can be reopened with a reason and an approval.
  - **Locking:** adjustments take the accounting settings (level 46, share), then the bank account row (level 48, `db.BankAccounts`, for update) which serialises the matching and reconciling of its statements; the unique index on the journal line is what stops two people clearing it twice.
  - **Partial clearing:** the day close journals of days closed before the per-payment detail below hold the total of a method for the day on one line. Several statement lines are cleared against that line in parts: the unique index on the journal line is replaced by a deferred check that what is cleared of a line stays on its side and within its amount, and the lines are listed with what is left (`remaining`). A part cleared without a statement line is not allowed (those are for whole lines).
  - **A line per payment in the day close:** from the day this change is deployed, the journal of a business day carries the account of the method (bank, card clearing, e-wallet, city ledger) **one line per payment** (source `PAYMENT`, `source_ref` the payment number, the description with the reference the guest or the bank gave) and one per city ledger receipt, instead of the total of the method. A payment voided the same day leaves no line. The guest ledger and advance deposits side stays one line per method, since nothing is matched with a bank there. Journals already posted keep their form (they are append-only); the partial clearing above covers them. This is what lets transfers be matched one by one, by amount or by reference.
  - **Card and e-wallet settlements:** card payments are received into the card clearing account (e-wallet and other payments into the other-payment account) until the acquirer pays them out in a batch net of its commission. From the bank statement line of the payout: the payment lines (CARD or OTHER_PAYMENT) are chosen, and a BANK journal dated the day of the line debits the bank account with what was paid, the **commission account** chosen with the difference and credits the clearing account with the payments (`card_settlements`, `card_settlement_items`: each payment line is settled once, which also keeps it from being offered again); the statement line is matched with the bank side. The payout may not exceed the payments chosen. This works for a line of money in that has nothing matched.
  - **Not included:** reading statement formats other than CSV (MT940, OFX), reversing a BANK journal from the screen (a mistake is corrected with a manual journal), and a foreign-currency bank account.
  - **Frontend:** Bank → Bank accounts, Bank statements (import with the rows that are wrong listed) and the reconcile screen (statement lines on one side, journal lines left to clear on the other, match one or several statement lines with one or several journal lines, undo, match automatically, post a line to the books, settle card and e-wallet payments, reconcile, reopen).

A charge that was never posted is posted as a charge. The folio page offers an adjustment only for the codes that have something posted and shows what is posted on the chosen one.   - **DataTable on TanStack Table.** `DataTable` keeps its props and slots, but its rows are now laid out by `@tanstack/vue-table` v8 (headless: row model, sorting, filtering; the markup stays ours). A column takes `filter: 'text' | 'select'` (a box or a choice under the header), optionally `filterValue(row)` (what the filter reads when the cell is custom) and `filterOptions`; filters match the text a cell *shows* (`1,500` finds an amount in English). With `manual` the table does not sort or filter itself: it keeps the rows as given and emits `sortChange` and `filterChange`, for a list that pages through the server. Column filters are on rooms, companies, folios, reservations, charge codes, suppliers, users and the in-house, arrivals and departures lists (`utils/status.ts` gives a status value its words, so a status filter lists "Open" and not `OPEN`). On a list that pages through the server (folios, reservations) a filter narrows the rows loaded so far; the search form above it still asks the server. Not built yet, but the engine is there: hiding and resizing columns, pinned columns, multi-sort, row selection, virtual rows (`@tanstack/vue-virtual`).
  - **Cleaning list: assign by floor.** Above the assignment form, one button per floor with open tasks ("Floor 2 (6)") ticks or unticks all the open tasks of that floor; floors can be added together (a housekeeper takes floors 1 and 2) and the usual "Give the ticked tasks to" sends one `POST /housekeeping/tasks/assign` with the ticked ids. The table has a Floor column with a filter. Frontend only: the assign endpoint already takes a list of task ids.
